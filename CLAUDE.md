# Лаборатория нестабильных порталов — контекст проекта

Тестовое задание на вакансию AI-first Developer в MOX, вариант «Лаборатория
нестабильных порталов».

**Срок по заданию — до 5 дней** (с возможностью согласовать продление до 10).
В первой редакции этого файла стояло «2–3 дня» — это была ошибка, сверено
с оригиналом задания.

- Живая версия: https://spisusha.github.io/portal-lab/
- Репозиторий: https://github.com/spisusha/portal-lab
- Исходное задание: https://mox-studio.notion.site/AI-first-Developer-MOX-38894a5391e18140a0edf7192f03723c

Страница задания в Notion собирается скриптами: обычная загрузка вернёт
пустой шаблон. Текст достаётся через публичный API
(`POST https://www.notion.so/api/v3/loadPageChunk`), причём вторая половина
страницы лежит в отдельном чанке — нужен второй запрос с курсором из первого.

## Перед началом работы

1. Прочитать `docs/PLAN.md` — чеклист статуса и метка «остановились здесь».
2. Прочитать `docs/worklog.md` — там честная история решений и ошибок.
3. Посмотреть `git log --oneline -15`.
4. Не переделывать то, что уже отмечено галочкой.

## Команды

| Команда | Что делает |
|---|---|
| `npm install` | установка зависимостей |
| `npm run dev` | локальный запуск на `/portal-lab/` |
| `npm test` | все тесты: домен + интеграционные UI |
| `npm run build` | `tsc -b` + сборка в `dist/` |

## Стек

Vite 6 + React 19 + TypeScript + Vitest 3. UI-тесты — Testing Library
поверх jsdom. Деплой — GitHub Pages через `.github/workflows/deploy.yml`
при push в `main`.

Важно: **vitest и vite должны оставаться совместимыми по мажору.** Связка
vite 6 + vitest 2 ломает сборку: npm кладёт vitest собственную вложенную
копию vite 5, и в проекте оказывается два несовместимых типа `Plugin`.

## Где что лежит

```
src/domain/    чистый TypeScript без React — вся логика и правила
  types.ts       модель портала, статусы, форматирование времени
  risk.ts        формула риска, ранги E–S, шкала RANK_SCALE, riskHeadline
  rules.ts       запреты с причинами, двухшаговое закрытие
  reducer.ts     переходы состояний, цикл времени, схлопывание
  recommend.ts   рекомендуемое действие
  summary.ts     счётчики и очередь внимания
  focus.ts       «что требует решения сейчас» + причина выбора
  seed.ts        три набора демо-данных
src/state/     useReducer + Context поверх домена
src/ui/        компоненты (только отрисовка)
  worldArt.ts    силуэты девяти миров в виде путей SVG
  WorldScene.tsx сцена мира и мелкий знак для строки списка
  PortalRing.tsx живой портал; шкала опасности формой, не только цветом
src/styles/    единая таблица стилей (дизайн-система «чернила и нефрит»)
docs/PLAN.md   чеклист статуса
docs/worklog.md черновик AI Worklog (витрина — вкладка в приложении)
```

## Правила, которые нельзя нарушать

- **Ни одной формулы и ни одного запрета внутри компонентов.** Расчёт риска —
  в `domain/risk.ts`, запреты — в `domain/rules.ts`, выбор срочного портала
  и текст причины — в `domain/focus.ts`. Компоненты только показывают то,
  что вернул домен.
- **Никакой случайности в домене.** Ни `Math.random`, ни `Date.now` — иначе
  сценарии перестанут быть воспроизводимыми и тесты поплывут.
- **Запрет объясняется до нажатия.** Кнопка недоступного действия —
  `disabled`, причина из `checkAction` выводится рядом. Никаких `alert`
  после клика.
- **Опасность никогда не кодируется одним цветом.** Ранг дублируется буквой,
  словом и формой — залитыми сегментами кольца в `PortalRing`. Это требование
  доступности, а не украшение.
- **Вся графика своя.** Внешних изображений, шрифтов и CDN в проекте нет и
  быть не должно: и из-за офлайн-работы, и из-за чужих прав.
- **Любая анимация выключается** через `prefers-reduced-motion` — правило
  уже есть в конце `theme.css`, новые анимации обязаны под него попадать.
- **Worklog ведётся по ходу.** Как только AI ошибся или предложил неудачное
  решение — сразу строка в `docs/worklog.md`. Задним числом это не
  восстановить, а честность здесь прямо оценивается.
- **Секретов в проекте нет** — внешние API не используются.

## Как проверять работу

Тесты и сборка обязательны, но их мало: половина ошибок этого проекта была
видна только глазами. Полезные приёмы, уже опробованные:

- **Прогон живого приложения через CDP.** В Node 24 есть встроенный
  WebSocket, поэтому браузером можно управлять без зависимостей: запустить
  Chrome с `--remote-debugging-port`, подключиться к `/json/list`, слать
  `Runtime.evaluate` и `Page.captureScreenshot`. Так проверяются сценарии,
  ошибки консоли и переполнение по ширине.
- **Ширину окна headless Chrome нельзя опустить ниже ~485 px.** Для проверки
  360/390 px нужен iframe фиксированной ширины внутри широкого окна, иначе
  скриншот просто кадрируется и выглядит «сломанным», хотя вёрстка цела.
- **Переполнение меряется, а не оценивается на глаз**:
  `document.documentElement.scrollWidth` против `clientWidth`.

## В конце каждой сессии

По фразе «зафиксируй прогресс»: проставить галочки в `docs/PLAN.md`,
передвинуть метку «остановились здесь», дописать `docs/worklog.md`,
сделать коммит с внятным сообщением.
